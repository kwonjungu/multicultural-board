# Opus 추가 실행 지침과 검증 하네스

## 1. 총괄에게 전달할 프롬프트

```text
기존 child-ux-20260911 설계와 바탕화면 ‘꿀벌교실_추가설계_20260911’를 함께 읽어라.
추가안 X01~X30은 신규 구현 완료가 아니라 후보/설계다. 기존 작업 트리를 먼저 확인하고
다른 작업자가 수정한 layout, FontSizeButton, child 토큰, 기억 카드 등을 덮어쓰지 마라.

자유롭게 더 좋은 구성을 제안할 수 있다. 대신 같은 과제 성공 조건으로 대안을 비교하고
데이터 보존·언어 지원·접근성·중복 지급·녹음 종료 계약을 약화하지 마라.

1) DATA가 learnerId/보관/보상/날짜 계약을 먼저 설계한다. 기존 DB 변경은 별도 마이그레이션이다.
2) AUDIO는 녹음 세션, 타이머, 권한 지연, TTS 재생을 독립적으로 고친다.
3) LEARN/READ/CLASS/CONTENT/WORLD는 확정된 계약을 소비해 화면을 만든다.
4) QA는 구현자와 독립적으로 아래 재현 fixture와 실패 주입 테스트를 작성한다.
5) 미술은 A01/A07/A22 대표 시안을 먼저 만든 뒤 승인된 스타일로 계열을 확장한다.
6) 생성 모델/비용/배치 규칙은 저장소 CLAUDE.md를 따른다. 프롬프트 문서는 생성 실행 승인이 아니다.

병렬 작업자는 각자 worktree/브랜치/포트/report 디렉터리를 사용한다.
공통 파일과 DB 계약의 수정은 총괄이 작은 커밋으로 통합하고 소비자에게 전달한다.
테스트 방 이름만 바꾸지 말고 실제 emulator/test 프로젝트 연결을 검증한다.
운영 1111에 테스트 쓰기, 삭제, 명렬표 변경, 보상 지급을 하지 마라.

각 작은 작업은 ‘원인 또는 가설/재현/실패 검사/변경/회귀/증거/미검증’을 제출한다.
P0는 재현과 회귀 테스트 없이 완료라고 하지 마라. 설계 문서와 프롬프트를 만든 것만으로
UI 구현이나 실제 에셋 제작 완료라고 보고하지 마라.
```

## 2. 분담과 충돌 방지

| 담당 | 소유 범위 | 소비 계약/경계 |
|---|---|---|
| DATA | learner adapter, 명렬표 보관, 지급 service, 날짜 service | lib/types·Firebase rules·API 공통 변경은 총괄 승인 커밋 |
| AUDIO | VocabRecorder, Interpreter 음성 service, 음성 세션 hook | UI 토큰은 기존 A 사용; VocabTest는 LEARN에 이벤트 계약 전달 |
| LEARN | VocabTest, 결과, 복습, 포트폴리오 | learnerId/policyVersion/recording API 소비 |
| READ | StorybookRoom, BookStudy, 읽기 보조 | 기존 세션 우선순위·종료 가드 유지 |
| CLASS | 토론, 그리기, 교사 운영, 연습방 | 명렬표 데이터 코드는 DATA 소유; RoomManagePanel 공동 직접 편집 금지 |
| CONTENT | 콘텐츠 대장, prompt/asset manifest, 감정 콘텐츠 | 이미지 생성 후 승인 파일만 public으로 반영 |
| WORLD | 공동 정원·개인 공간 | 기존 D render plan/E renderer 및 DATA 지급 계약 소비 |
| QA | tests/addendum, reports/addendum | 제품 코드 수정 대신 재현/실패 증거 제출 |

기존 팀 B/C/D/E/F와 겹치는 파일은 새 팀을 같은 파일에 바로 투입하지 않는다. 예: 기존 E가 BeeVillage를 작업 중이면 WORLD는 공동 정원 데이터/fixture/별도 패널만 작성하고 E에게 연결 patch를 보낸다. 별도 worktree도 논리적 충돌을 없애지는 못한다.

실행 파동: (0) 계약/fixture → (1) X01~04와 음성·학습 정책 시안 → (2) P1 읽기/교사/회복 → (3) 콘텐츠/자산 승인 → (4) P2 실험 → (5) 통합 검증. 동시 슬롯이 3개면 DATA/AUDIO/QA부터, 이후 LEARN/READ/CLASS 순으로 배정한다. 이미지 생성 대기 때문에 데이터 오류 수정이 멈추지 않도록 한다.

## 3. P0 최소 재현과 독립 기대값

아래는 구현할 검사 명세다. 이번 추가 설계 단계에서는 제품 테스트를 실행하거나 새 오류를 운영에서 재현하지 않았다.

| Test ID | 고정 입력/행동 | 기대 결과 |
|---|---|---|
| ADD-ID-01 | 같은 이름 학생 2명, 각각 서로 다른 스티커/단어/녹음 | 조회·갱신·전환 시 서로 기록이 섞이지 않음 |
| ADD-ID-02 | 학생 이름 수정→새로고침→다른 기기 입장 | ID 유지, 모든 연결 기록과 작품 동일 |
| ADD-ROSTER-01 | 명렬표 제거→보관→복원 | 원본 콘텐츠/개수/hash 동일; 완전 삭제 호출 0회 |
| ADD-MIGRATE-01 | 같은 이관 입력을 2번 실행, 중간에 실패 후 재실행 | 누락·중복 0; 모호한 매핑 자동 병합 금지 |
| ADD-MIC-01 | A t0 시작/t2 중지, B t3 시작, 가상 시각 t15/t18 | t15 B recording, t18 B stop; A 타이머가 B에 영향 없음 |
| ADD-MIC-02 | getUserMedia pending→닫기→resolve(stream) | stream 모든 track stop, recorder/STT/상태 알림 없음 |
| ADD-MIC-03 | A 예문 녹음→B 예문 전환→A onstop/STT 지연 응답 | B 내용/저장 포인터 불변, A 취소 결과는 폐기 |
| ADD-CLAIM-01 | 동일 eventId 두 client 동시 claim | 잔액/XP 각 1회 반영, 원장 1개 |
| ADD-CLAIM-02 | 선점 후 지급 실패, 지급 후 완료 기록 실패 각각 주입 | 재처리 후 1회 지급, 영구 미지급/중복 0 |
| ADD-DAY-01 | 교실 자정 직전 화면 열기→자정→탭 복귀 | 목록/구독/claim 동일 dayKey, 오래된 보상은 원래 날에 귀속 |
| ADD-SUB-01 | 동일 경로 listener 2개→하나 unmount→데이터 갱신 | 남은 listener 정상 수신 |
| ADD-TTS-01 | HTMLAudio fallback 재생 중 WebSpeech 언어로 변경 | 전체 활성 음성 최대 1개, 닫기 후 0개 |

재현 fixture에는 fake clock, controlled promise, fake MediaStreamTrack.stop spy, fake recorder instance별 상태, 실패 단계별 지급 adapter를 사용한다. 구현 함수의 반환값을 그대로 기대값으로 쓰지 않는다. 사용자 행동과 시간 경계에서 기대값을 독립 정의한다.

## 5. 작은 모델에게 줄 작업 예시

```text
TASK X03-a: 녹음 제한시간이 다른 녹음을 중단시키지 않도록 수정
읽기: VocabRecorder.tsx, ADD-MIC-01~03, 기존 음성 정책
수정 허용: VocabRecorder.tsx, 전용 녹음 세션 hook 1개
금지: STT provider 교체, 녹음 길이 정책 변경, 임의 타이머 대기 증가, 테스트 기대값 완화
절차:
1) t0 A 시작/t2 중지/t3 B 시작/t15 B 중단 가능성을 fake clock으로 재현
2) timeout은 녹음별 소유, callback은 같은 recorder/session에만 작동하도록 수정
3) 종료/취소/unmount cleanup과 늦은 권한 resolve 처리
4) ADD-MIC-01~03 실행 후 실제 지원 브라우저에서 녹음/재생 별도 검증
제출: 재현 전후, 파일, 명령/exit code, 로그, 실기기 미검증 목록
```

P0 구현자가 직접 자신의 acceptance 테스트 파일을 약화하지 못하게 QA 소유로 둔다. 한 패킷은 제품 파일 최대 3개, 조건 최대 5개, 변경 이유 한 문장으로 축소한다. 두 번 실패하면 축소 재현과 원인 후보를 총괄에게 넘긴다.

## 6. 결과 기록과 출시

매 결과에는 기준 SHA, 작업 ID, 변경 파일, 재현 상태(코드 후보/테스트 재현/실기기 재현), 실행 명령/cwd/exit code, 증거 경로, 미검증, 데이터 영향, rollback을 남긴다. 실패와 미실행을 별도 기록하고 미실행을 pass로 바꾸지 않는다.

계약→로컬 fixture→테스트 프로젝트→미리보기→교사·아동 과제 관찰→배포 후보 순서로 진행한다. X01/X02/X04 데이터 전환은 UI 배포와 별도 시행 계획을 세운다. 삭제/이관/유료 생성의 실제 실행은 기존 사용자 승인 범위와 저장소 규칙을 다시 확인한다.

이미지 제작 완료는 ‘생성됨’이 아니라 승인된 원본+최적화본+manifest+화면 연결+시각 테스트다. 전체 확장 완료는 30개 후보를 모두 구현했다는 뜻이 아니라 채택/보류 이유와 검증 결과를 명확히 결정했다는 뜻이다. 채택한 필수 기능은 끝까지 구현·검증해야 한다.
